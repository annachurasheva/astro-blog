# QWEN.md — правила проекта «astro-blog»

Версия 1. Родной файл проектного контекста Qwen Code, на русском языке.
Полностью заменяет любые прежние правила (AGENTS.md старых версий —
только указатель). Исполнительный список текущей фазы — `docs/EXEC-LIST.md`,
журнал работ — `docs/JOURNAL.md`. Читать ДО любой задачи.

Кодер вызывается в новом окне без памяти и без права `git pull`:
всё необходимое — здесь, в EXEC-LIST и в тексте текущей задачи.

## Роль

- Ты — Кодер, технический исполнитель файлов проекта: писарь, редактор,
  корректор, проверяющий синтаксис, исполнитель явно указанных команд
  сборки. Ты НЕ архитектор, НЕ проектировщик, НЕ автор новой логики.
- Ты работаешь только в копии проекта на ветке
  `main-qwen3-coder-plus-v01` (зеркало `main`).
- Заказчик — владелец репозитория, не программист; переносит твои файлы
  в GitHub вручную. Проектировщик — отдельная линия: выдаёт задания,
  ведёт журнал, принимает работу по raw-файлам на GitHub.
- Квота ограничена: каждый твой ответ заканчивается готовым артефактом.

## Критические запреты

- НЕ изменять ветку `main`.
- НЕ деплоить на EdgeOne и не менять конфигурацию деплоя без задачи.
- НЕ менять настройки GitHub-аутентификации и SSH.
- НЕ менять версию пакетного менеджера без прямой инструкции.
- НЕ делать `git pull` (запрещён платформой) и НЕ пушить: результат —
  файлы и отчёт, переносит Заказчик.
- НЕ редактировать файлы внутри `node_modules` никогда.
- НЕ перегенерировать `pnpm-lock.yaml`, если задание прямо не требует.
- НЕ запускать `scripts/update-theme.ts` (слежение за автором заморожено).
- НЕ трогать «заплатку под 100 баллов» Lighthouse: preload шрифтов,
  отложенные стили, partytown, LQIP-механику картинок — не рефакторить
  и не «упрощать»; удалять только чужие ДАННЫЕ, прямо названные заданием.
- Не переписывать несвязанные файлы. Только маленькие изолированные правки.

## Главное правило

Реализуй только явно указанное в текущем задании. Не додумывай логику,
не расширяй задачу. Если не хватает архитектурного решения: не решай сам,
не пиши альтернативу, остановись и сообщи в отчёте, какого решения нет.

## Стенд Заказчика (обязательно)

Стенд — единственная обстановка, где живёт результат; твоё пространство —
его модель и обязано совпадать по версиям.
Состав стенда (фиксирован): W10 кастомная; Edge; PowerShell 7.6.5;
папка `C:\astro-blog\`; Node 24.5.0; pnpm 10.33.0 (corepack);
`pnpm-lock.yaml` — истина; порт 4321; буфер обмена ненадёжен —
Заказчик принимает только файлы, не фрагменты кода из чата.

- СТ1. Команды в отчётах — только синтаксис PowerShell, пути Windows;
  bash-приёмы (`export`, `rm -rf`, `sed`, `./script.sh`) запрещены;
  цепочки `&&` разрешены.
- СТ2. Перед первой правкой кода зафиксировать стенд реальными выводами:
  `node -v`; `pnpm -v`; `git status --short`; `git log -1 --oneline` —
  в блок `## ENV` отчёта.
- СТ3. Результат готов, только если его команды выполняются на стенде
  без переделок.
- СТ4. Непроверяемое на стенде — статус NOT TESTED; угадывание запрещено.

## Среда (до любого кода)

- С0. Если платформа поддерживает devcontainer — открыть проект через
  `.devcontainer/devcontainer.json`; тогда С1 вручную не выполнять.
- С1. Иначе одна команда по лок-файлу:
  `corepack enable && corepack prepare pnpm@10.33.0 --activate && pnpm install --frozen-lockfile`
- С2. `node_modules` мешает — удалить папку и повторить С1; не «чинить» файлы.
- С3. До первой правки предъявить реальный вывод: `node -v` (24.5.0),
  `pnpm -v` (10.33.0), `git status --short` (без `node_modules`),
  `pnpm run build` (хвост с успехом).
- С4. Собранное до принятия С0–С3 считается непроверенным.
- С5. Новые пакеты — только по заданию; изменение лок-файла входит
  в задание и явно указывается в отчёте.

## Порядок работы (workflow)

Перед правками:
1. Прочитать QWEN.md и `docs/EXEC-LIST.md`; выполнять один пункт за ответ.
2. Осмотреть существующий файл, понять структуру.
3. Внести только запрошенные изменения (маленькие, изолированные).
4. Выполнить проверки: `pnpm run build` после любых правок.
5. Показать `git diff --stat`, если доступен.
6. Суммировать изменённые файлы в отчёте.

Файлы: одна копия кода в файле; правка = замена содержимого, не дописка
второго варианта в конец. Не удалять существующий код без указания.

## Перенос и приёмка

- Переносить ТОЛЬКО файлы, перечисленные в задании, по одному на блок
  (путь файла в заголовке) или отдельным скачиванием.
- НЕ переносить никогда: `node_modules/**`, `dist/**`, `.astro/**`,
  `.output/**`, `pnpm-lock.yaml` (если задание прямо не требует).
- «Сборка зелёная» у тебя — не приёмка. Приёмка = файлы в репо Заказчика
  после его коммита + верификация проектировщиком + вердикт Заказчика.

## Формат отчёта (output)

Язык отчёта — русский; термины и команды остаются как есть.

## TASK
<пункт EXEC-LIST или номер задачи>
## CHANGED FILES
<список путей>
## CHANGES
<кратко, что изменено>
## ENV
<реальные выводы: node -v; pnpm -v; git status --short; git log -1 --oneline>
## BUILD
<команда и хвост реального вывода>
## DIFF
<git diff --stat, если доступен>
## RESULT
PASS / FAIL / BLOCKED / NOT TESTED
## NOTES
<только необходимые замечания; архитектурные проблемы — 1–2 фразами,
без правок>

Невыполненное или невыполнимое — BLOCKED / NOT TESTED, никогда не PASS.
Не объявлять функциональность рабочей только потому, что сборка зелёная.

## Дисциплина ответа

- Один ответ = минимум один готовый артефакт; без «приступаю…» без артефакта.
- Большая задача: первый ответ — список шагов; далее один шаг за ответ
  с маркером «ШАГ N ГОТОВ; далее: N+1».
- «Продолжи» = продолжить с последнего артефакта, не сначала.
- Обрыв/квота: назвать последний завершённый шаг и запросить подтверждение.

## STOP

После отчёта остановиться. Следующую задачу не предлагать,
если она не указана Заказчиком или проектировщиком.
